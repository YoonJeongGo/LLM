## 이전에 빠진 내용이 실제로 전달됐는가

- **N01 보충 s6~s9:** zone ASC → delta DESC → parcel DESC, 앞 키가 같으면 다음 키를 비교하는 규칙을 유지한다. s7에서 앞 기준이 같은 행 안에서 delta DESC의 NULL은 뒤라고 설명한다. s8에서 P5의 -4와 P1의 NULL을 직접 비교하며 P5가 앞서는 이유를 읽는다. s9에서 P6의0과 P3의-4를 비교하고, 현재 결과에는 모든 정렬 키가 같은 행이 없으며 완전 동점의 내부 순서는 보장되지 않는다고 말한다. 같은 원본4쌍이 비교 표에 표시된다. 별도 반복에서도 동일한9단계가 자연 종료·복귀했다.
- **N02 보충 s8~s10:** s9에서 M3/M4의 batch3·qty5까지 같은 뒤 item M3/M4를 ASC로 비교한다. s10에서 M1/M8의 batch2·qty0까지 같은 뒤 item M1/M8을 비교한다. 두 실제 동점쌍과 중간 batch3→2 전환이 원본행 번호·수치와 같은 비교 표로 연결된다.
- **N02 보충 s11:** “설명용 새 예시”, “원본 표와 SQL은 보존”, “별도의 빈 표”라고 명시한다. 빈 표0행과 [SUM(qty)=NULL, COUNT(qty)=0, COUNT(*)=0] 표를 표시하고 같은 결과를 읽었다. 실제 원본 결과4행을 빈 결과라고 바꾸지 않았다.

원래 잘되던 P3 포함·P2 제외·이름으로 지정한 P1 NULL/P6 숫자0 비교, M1 포함·M2 NULL 제외·M7 같은0이지만 status 때문에 제외되는 이유도 실제 원본 값과 일치했다. NULL 비교를 원래 SQL 조건 변경으로 추가하지 않았다.

## 모델 오류와 앱 설명의 구분

N01 보충 원시 SQL은 맞지만 원시 설명은 P1/P6을 제외한다고 잘못 말한다. 실제 앱 대사는 rush=1이 TRUE이므로 OR가 TRUE가 되어 둘 다 포함된다고 설명했다. 같은 오류는 별도 반복의 원시 설명에도 남았다.

N02 초기 원시 IN(0,5)는 원문의0 또는5 이상과 다르다. 현재 표의 결과가 우연히 같아도 별도의 가상 qty6 반례에서 차이가 나므로 원시 정답으로 세지 않았다. N02 보충은 그 수량 조건을 통째로 빠뜨려 실제 결과도 틀렸다. 앱은 원문에서 확인된 의도로 교정한 SQL을 다시 검증했고, 원래 조건의 행 계산·대사·판서를 사용했다. 교정은 raw response와 다른 origin으로 보존돼 있다.

## 판정 방법과 남은 경계

새 assessment는 terminal actual과 입력·소스 동결 동일성을 확인한 기존 postrun_review.py로 생성했다. 초기2/보충2 및 사전 등록한 반복1의 request→message→lesson→playing을 각각 연결했다. 원래 동결 기준 문구는 바꾸지 않았다. 의미 판정은 AI가 실제 대사와 판서 내용을 읽고 요구별 관련 단계·인용·이유를 기록한 것이다. 완전 통과 집계는 AI_TEXT_AND_BOARD_REVIEW_PASS 또는 AUTOMATED_PLAYBACK_RESTORE_PASS의 정확한 일치만 사용한다. PARTIAL_NOT_FULL_PASS 접미사를 잘못 통과로 세던 이전 오류를 반복하지 않았다.

수집기 전체 화면 검사도 이 두 사례에서 board/diagram/pointer/restoration/all-steps 항목을 통과했지만, 이 내용 판정이 모든 시점의 표시 지연·사람 가독성·교육성을 대신 승인하지 않는다. 특히 final06은 큰 actual JSON을 동기 저장하는 검사 경로의 route 지연이 확인됐다. 보충 종료→원래 음성 사이3~5초 관측은 계측 부담이 분리되지 않았으며, 복귀 성공2/2를 G05 공백 통과로 바꾸면 안 된다. final07의 로깅·재생 경로 비교와 최종 실제 결과는 별도 대기다.

N03 재채점·독립 점수 합산·운영 DB/API/WAV 직접 읽기·모델/음성 실행은 이 판정 작업에서 하지 않았다. 운영 문서와 제품 코드는 변경하지 않았다.
