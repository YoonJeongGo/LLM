# 후속 개발 계약: 작동하는 MVP → 내용과 상호작용을 검증하는 튜터

## 0. 범위와 원칙
사용자의 질문에 그 자리에서 설명을 구성하는 제품이다. 모든 분야의 사전 강의 제작,
자체 기반모델 사전학습, 멋진 신경망 애니메이션, 무한 자동학습을 이번 목표로 바꾸지 않는다.
첫 분야는 기초 데이터베이스다. 지원 범위는 밝히되 질문을 정해진 메뉴로만 강제하지 않는다.

기존 코드, 검증 기록, 기본 모델 및 승격되지 않은 어댑터를 보존한다.
추가 학습 없이 원인 진단·검색·도구 검증·대사/판서 연결을 먼저 개선한다.
학습을 보류한다는 것은 모델 개발을 포기한다는 뜻이 아니다. 잘못된 원인을 특정하기 위한 순서다.

절대 조건:
1. 허위 성공·가짜 응답·인간 검토 대행 표시 금지.
2. 사용자 파일·개인 정보·기존 환경 보호. 토큰은 읽어 사용할 수 있어도 출력하지 않는다.
3. 평가 정답 누수·질문 ID별 하드코딩·원래 실패 기록 삭제 금지.
4. 추가 학습·신규 대형 모델·유료 서비스·외부 업로드 자동 실행 금지.
5. 학습 결과와 앱 결과, fixture 검사와 실제 모델 검증을 구분한다.

현재 Windows/Python 3.12/CUDA 조합이 작동한다면 유지한다.
새로운 기술 문서가 나왔다는 이유로 Torch·Transformers 전체를 업그레이드하지 않는다.
공식 문서 확인이 필요하면 설치된 버전에 맞춰 검토한다.

## 1. 시작 기록 및 자원 제한
Git 상태, 기존 지침, 실제 실행 중인 모델/어댑터, 런타임과 저장 경로를 먼저 조사한다.
존재하지 않는 코드 파일명을 가정해 리팩터링하지 않는다. 기존 인터페이스에 맞춰 최소 변경한다.

작업 산출물은 기존 runs 체계 아래 phase2/<run_id> 또는 그에 상응하는 단일 경로에 둔다.
모델·업로드의 대규모 복사본을 만들지 말고, 코드 변경과 결과 추적만 추가한다.
실제 데이터 루트가 D의 .local인지 F인지 설정과 실파일로 확인한다.
F가 설정된 경우 드라이브 존재만 아니라 의도한 볼륨인지 확인한다.
없을 때 C나 D에 대신 모델을 받는 fallback은 금지한다.

공간 정책은 이번 명세에서 decimal GB로 표시한다:
- 모든 위치를 합친 프로젝트 귀속 사용량 최대 50,000,000,000바이트
- 40,000,000,000바이트부터 경고
- C 여유 50,000,000,000바이트 유지
기존 구현의 단위가 다르면 차이를 보고하고 명확히 표시하되 사용자 데이터를 삭제하지 않는다.
캐시·환경·미디어·임시 복사본도 포함한다. 공유 캐시는 귀속 범위와 미확인을 따로 보고한다.

GPU 작업은 기존 단일 소유 큐를 통해 실행한다. 별도 프로세스를 몰래 병렬 실행하지 않는다.
한 모델 요청은 최대 300초, 동일 실패의 자동 수정 요청은 1회 이내로 제한한다.
실제 모델/음성/사진 검증의 누적 GPU 작업 시간 예산은 이번 회차 90분이다.
이는 완료시간 약속이 아니라 자동 실행 상한이다. 사용자가 더 작은 한도를 정했으면 그 값 우선.
상한에 도달하면 미실행을 남기고 가능한 CPU/UI 작업을 마친다. 무한 평가 반복 금지.
실제 음성 생성은 필요한 새 클립 최대 12개, 실제 사진 추론은 최대 4개로 시작한다.
초과가 필요하면 사유와 미검증 항목을 남긴다. 동일 음성은 올바른 캐시 키일 때만 재사용한다.

## 2. 단계 A — 3/11의 원인을 먼저 조사
### A1. 이전 결과 보존
기존 12문항, SQL 11문항, 평가 설정, 답변 원문, 판정 상세를 읽는다.
실제로 이 구성인지 확인한다. 12번째 문항의 종류를 추정하지 말고 표시한다.
기존 3/11, 잘림 0→2 및 원래 지표를 수정하지 않는다.
기존 채점기가 잘못됐다면 old_protocol과 corrected_protocol 결과를 모두 남긴다.

### A2. 문항별 실패표
각 항목에 질문·주어진 스키마·기대 결과·원시 응답·추출 SQL·실행 결과·실패 사유를 기록한다.
분류는 복수로 가능하며 확인된 근거와 추정은 구분한다.
- 실제 개념/계산/SQL 의미 오류
- 존재하지 않는 표/열 또는 잘못된 별칭 참조
- 정답인데 추출/비교 로직이 오판
- SQL 작성 문제/결과 계산 문제/개념 설명 문제의 과제 형식 혼동
- max_new_tokens 등 출력 제한으로 인한 불완전 출력
- chat template/assistant 시작/EOS/non-thinking 불일치
- RAG 자료 오검색/낡은 내용/문제의 스키마 덮어쓰기
- DBMS 차이 또는 기준 SQL/정답 자체의 오류
- 근거 부족으로 원인 미확정

원래 평가의 같은 조건(256토큰 등)을 유지한 결과와 개선 설정의 결과를 별도로 기록한다.
출력 제한을 바꿨다면 모델이 똑똑해졌다고 말하지 않는다.
선택한 설정이 강의용 긴 JSON 때문에 문제였는지 확인한다.
긴 구조화 출력과 간단한 정답 생성을 분리해 원인을 좁힌다.

단어 일치나 코드 블록 유무만으로 정답을 판정하지 않는다.
동치 SQL, NULL, 중복행, 빈 결과, 정렬 조건, 숫자 타입/오차를 규칙에 따라 비교한다.
순서 요구가 없으면 행의 중복을 유지한 다중집합으로 비교하고,
ORDER BY나 명시적인 출력 순서 요구가 있으면 순서를 검증한다.

### A3. 중간 판단
오류를 확인하면 재현 테스트를 추가한 뒤 수정한다.
입력·채점·설정 문제와 실제 모델 능력 문제를 섞지 않는다.
자료/검증 도구 개선 후에도 정확한 답을 못 하면 그 한계를 그대로 남긴다.

## 3. 단계 B — 정답 검증과 수업 데이터 연결
### B1. 질문의 원본을 보존
학생 입력에서 문제 종류, DBMS, 표/열/값, SQL, 구하려는 결과, 빠진 조건을 구조화한다.
이 구조는 파서나 LLM이 잘못 만들 수 있으므로 원문·버전·출처를 함께 유지한다.
사진의 OCR 결과와 학생이 확정한 원문은 별도 revision으로 관리한다.
학생이 수정하면 이전 계산/음성/판서 계획을 무효화한다.

RAG에서 가져온 예제의 컬럼명을 학생 문제의 컬럼으로 덮어쓰지 않는다.
모델이 답을 맞추려고 원본 데이터나 질문의 SQL을 몰래 고치지 않는다.
학생이 오류 있는 SQL의 설명을 요청한 경우 원문 오류 자체를 설명하고,
수정안은 별도로 표시한다.
개념 질문에 필요한 예시는 새로 만들 수 있지만 반드시 '설명용 새 예시'로 표시한다.
원래 문제의 정답을 구하는 데 표가 없으면 숫자를 만들어 넣지 않는다.

### B2. 검증 범위를 분리
단순한 validate=true 하나 대신 다음을 따로 기록한다.
- 입력 확인 상태
- 실제 스키마/이름 해석 검사
- 실행 여부와 DBMS
- 계산/결과 일치 검사
- 질문의 의도 충족에 대한 확인 범위
- 설명 문장과 계산 내용의 일치
- 사람이 읽고/듣고 검토했는지

SQL이 실행됐다는 사실만으로 질문을 올바르게 풀었다고 표시하지 않는다.
학생이 준 SQL의 결과를 묻는 문제는 그 SQL을 안전하게 실행한 결과가 근거가 될 수 있다.
자연어에서 SQL을 작성하는 문제는 잘못된 SQL도 실행되므로 의미 확인이 별도로 필요하다.
일반적인 모든 SQL 의미 검증기를 새로 만드는 것은 이번 범위가 아니다.
검증 가능한 기초 연산 범위를 밝히고, 검증 밖 내용을 확정적 강의로 포장하지 않는다.

정답이 알려진 테스트에서는 독립된 기대 결과와 비교한다.
실사용에서 기대 결과를 모르는 경우 '기대 결과 일치 검증 완료'를 만들지 않는다.
같은 LLM에게 다시 '맞니?'라고 물은 결과만으로 독립 검증됐다고 처리하지 않는다.

### B3. SQL 실행 안전
현재 격리된 SQLite 검사기를 재사용한다. 앱의 대화 DB나 사용자 DB에 실행하지 않는다.
읽기 질의는 기존 제한·timeout·행수 제한을 유지한다.
DDL/DML 예제를 실행할 필요가 있으면 앱과 분리된 일회용 :memory: DB에서만 수행한다.
호스트 파일 접근, ATTACH/DETACH, 확장 로딩, 임의 함수/PRAGMA 등 탈출 경로를 막는다.
사용자의 SQL이 안전 범위 밖이면 실행하지 않고 검증 범위 한계를 알린다.
Oracle 고유 동작을 SQLite 성공으로 검증했다고 보고하지 않는다.

### B4. 없는 열과 오답의 강의 전파 차단
SQL 스코프/별칭/CTE를 고려하여 원본에 없는 참조를 감지한다.
단순 문자열 목록 검사만으로 유효한 별칭이나 COUNT(*)를 오탐하지 않는다.
현재 파서/DB prepare를 활용하되, 검증을 위해 위험한 SQL을 사용자 DB에 실행하지 않는다.
오류 시 알려진 원본 스키마와 오류를 바탕으로 수정 요청 최대 1회만 허용한다.
그래도 해결되지 않으면 틀린 숫자를 음성·칠판에 내보내지 않고 상태와 부족한 조건을 알린다.
거절이 늘어난 만큼 coverage도 함께 기록한다. 전부 거절하는 앱으로 성공시키지 않는다.

### B5. 답·표·음성을 같은 근거에서 생성
해설에 사용하는 원본 표, 중간 계산, 최종 결과를 하나의 공유 데이터 구조로 보존한다.
셀/행/열에는 안정적인 ID를 둔다. 모델이 판서용으로 숫자를 다시 자유 생성하게 두지 않는다.
COUNT, SUM, AVG 등 지원하는 기초 연산은 실제 입력값으로 근거 계산을 연결한다.
예: AVG는 포함되는 값·합계·개수를 보여주고 그 나눗셈 결과와 표를 연결한다.
설명상 논리적 처리 순서와 DB의 실제 물리 실행 순서는 같다고 주장하지 않는다.

개념/풀이 문장의 모든 진실성을 자동 증명했다고 과장하지 않는다.
결과 표와 숫자는 프로그램의 확정값으로 넣고, 나머지 설명은 검토 범위를 표시한다.
틀린 최종 정답을 숨긴 채 예쁜 판서만 보여주는 방식은 금지한다.
정확한 텍스트가 있더라도 음성/판서가 실패하면 그 경로는 실패로 표시한다.

## 4. 단계 C — 실시간 강사의 상호작용 완성
### C1. 첫 설명과 지속성
짧은 질문에는 짧은 답부터, 필요하면 예시를 확장한다.
한 번에 거대한 강의 JSON/오디오를 모두 생성하기보다
핵심 답과 첫 2~4개의 작고 완결된 설명 단위를 준비하고 검증된 단위부터 재생한다.
긴 30분 수업을 만들고 기다리게 하지 않는다.
단, 첫 시작을 빠르게 보이게 하려고 검증 전 오답을 먼저 말하지 않는다.
지금 확인 중이라는 짧은 UI 표시를 '첫 유효한 강의 시작'으로 측정하지 않는다.

작은 모델에 모든 역할을 긴 프롬프트 하나로 몰아넣지 않는다.
현재 파이프라인을 프로파일링한 뒤 답의 사실/계산, 수업 단계, 렌더링을 적절히 분리한다.
분리 단계가 늘어나 오히려 느려지면 호출 수와 모델 전환 비용을 측정해 줄인다.
8GB GPU에서 LLM/TTS/비전의 동시 적재를 강제하지 않는다.
매 문장마다 모든 모델을 다시 로딩하는 구현도 피한다.
기존 worker 재사용·작은 버퍼·재생 중 다음 단위 준비 등을 실제 메모리와 지연으로 선택한다.
새 TTS/대형 모델 다운로드를 해결책으로 자동 실행하지 않는다.

### C2. 판서·그림·몸짓
필수 표현: 표, 셀/행 강조, 텍스트/코드, 선, 화살표, 사각형, 원/타원, 묶음 괄호.
좌표/대상/도형 속성이 제한된 안전한 데이터만 렌더러에 넘긴다.
임의 JavaScript/HTML/SVG 실행과 외부 이미지 URL 자동 로딩을 허용하지 않는다.
같은 원본 표에서 행 묶기, 열 추가, 선택된 값 표시를 단계적으로 보여준다.
보조 그림은 손그림풍으로 가능하되, 글자와 수치의 가독성을 우선한다.
모든 글자의 실제 한글 획순 생성은 이번 필수 조건이 아니다.

기본 캐릭터라도 학생 보기→칠판 보기→쓰기→가리키기→설명 동작을 구분한다.
선/도형을 그릴 때 펜 끝과 그려지는 경로가 같은 좌표/시간 데이터를 사용하도록 한다.
텍스트의 글꼴 기반 노출을 실제 획순 생성이라고 표시하지 않는다.
입 움직임은 실제 오디오에 연결하고 음성 단위/문장 단위 정렬 수준을 표시한다.
리사이즈/확대 후에도 손이 다른 셀을 가리키지 않도록 한다.

### C3. 내용이 있는 칠판에서 추가 질문
원본 표와 한 개 이상의 강조/그림이 이미 보이는 순간에 질문한다.
말/입/진행 중 쓰기 동작을 멈추고, 기존 판서의 element ID와 내용·위치를 보존한다.
새 질문을 독립된 처음 질문처럼 처리하지 않고 현재 단계/선택 셀/학생의 막힌 지점을 전달한다.
보충 설명은 공간을 분리하거나 별도 오버레이/페이지로 구성하여 원래 표를 불필요하게 지우지 않는다.
원래 설명으로 돌아오면 판서 객체와 재생 단계가 일관되게 복원돼야 한다.
의도적으로 사용자가 수정한 내용은 stale snapshot으로 되돌리지 않는다.
질문 두 번 연속, 취소 후 새 질문, 늦게 도착한 이전 응답도 검증한다.
request/lesson epoch로 지난 텍스트·오디오·판서 이벤트가 새 상태를 덮지 못하게 한다.

학습/GPU 점유 중 409가 반환되더라도 사용자가 작성한 질문은 입력창 또는 로컬 draft에 남겨라.
예약 전송을 자동 동의로 간주하지 않고 재전송 버튼 또는 분명한 대기 상태를 제공한다.
문서에 없는 녹음/음성 입력 기능을 몰래 필수 구현으로 늘리지 않는다. 이번 입력은 텍스트/사진이다.

### C4. 사진
원본/인식 결과/수정/확정 절차를 유지한다.
표의 행·열·NULL·연산자·선택지 구조를 최대한 보존하고 불확실한 항목은 확인 대상이다.
인식 모델의 자기 확신만으로 정확도를 보장하지 않는다.
잘린 문제는 확정 버튼을 눌렀다는 이유만으로 내용이 완전해졌다고 판단하지 않는다.
빠진 조건을 구체적으로 묻고 원본 문제의 답을 만들어내지 않는다.
사진을 지적하기 위해 표시한 박스와 실제 인식된 영역을 구분한다.

## 5. 단계 D — 측정·비교·품질 판정
모델 단독/기존 어댑터, 모델+RAG, 모델+RAG+검증 도구를 다른 모드로 보고한다.
도구를 붙여 맞힌 것을 모델 자체가 학습해서 똑똑해졌다고 표시하지 않는다.
기존 어댑터는 새 근거 없이 기본 적용하지 않는다.

동봉 18개 SQL 자료는 공개 개발 회귀 테스트다. 비공개 홀드아웃이나 교육 정확도 인증이 아니다.
expected_rows, reference_sql 등 정답 필드는 추론 프롬프트/RAG에서 분리한다.
주어진 SQL의 결과를 묻는 과제라면 question_sql은 문제의 일부이므로 전달할 수 있다.
자연어→SQL 과제에서는 reference_sql을 모델에 제공하지 않는다.
질문 ID/문구를 조건으로 정답 또는 미리 작성된 수업을 반환하지 않는다.

수정 후 평가 예산 안에서 새로운 별도 문제 묶음을 고정해 시험한다.
범위 예: 개념 4, 계산/질의 6, 정보 부족/DBMS 차이 2개 이상.
이것도 소규모 진단이며 일반 성능으로 외삽하지 않는다.
평가를 보고 코드를 고쳤다면 그 묶음은 이후 development로 내려 표시한다.
AI가 만든 설명을 human-reviewed라고 표시하지 않는다.

정답률 외에 정답/오답/질문 필요/안전 중단/잘림/실행 실패 수를 모두 보고한다.
유효하고 답할 수 있는 질문에 얼마나 답했는지 coverage를 별도 기록한다.
사용자가 요청한 문제를 못 풀고 예시 문제로 바꿔 풀면 원래 문제 성공으로 계산하지 않는다.
표시 결과·발화 대사·판서 숫자·원본 조건의 일치 여부를 검사한다.

지연은 cold/warm 각각 요청 수와 실제 값을 기록한다.
입력 확정→모델 준비→핵심 답 검증→첫 유효 음성/판서→전체 종료를 나눈다.
질문 중단 시 음성 정지까지, 보충 설명 시작까지, 원강의 복귀까지 따로 기록한다.
모델 토큰 속도만으로 실시간 강의 속도를 평가하지 않는다.
표본이 적으면 모든 값을 보여주고 p95를 안정적인 성능 지표처럼 제시하지 않는다.
수업 시작의 10초 이내, 중간 질문 시 로컬 재생 정지 0.3초 이내를 초기 UX 목표로 측정하되
달성 보장이나 하드웨어 한계라고 추정하지 않는다. 못 달성하면 병목과 실제값을 적는다.

최종 수정 뒤 전체 기존 테스트와 영향 받는 실제 브라우저/모델 경로를 다시 확인한다.
브라우저 검사 이후 코드를 바꿨으면 그 검사의 유효 범위를 갱신한다.
기존 test count를 맞추기 위해 테스트를 삭제하거나 실패 조건을 약화하지 않는다.
