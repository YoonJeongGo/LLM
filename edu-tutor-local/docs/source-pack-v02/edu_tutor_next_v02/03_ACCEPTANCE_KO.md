# 실제 수업 기준 인수 검사

아래는 이번 프로젝트의 제한된 범위 검증이다. 모든 SQL/교과에서 정확함을 증명하지 않는다.
데모 fixture 결과와 실제 모델 출력/오디오/브라우저 결과를 구분한다.
기존 12문항은 회귀 기록으로 보존하며, 이 문서의 검사를 그 결과와 합쳐 과장하지 않는다.

## A. 필수 시나리오

### T01. 갑자기 묻는 개념: DDL
입력 예: 'DDL이 뭐였지? 사람 추가하는 것과 칸 추가하는 게 헷갈려.'
- 첫 핵심 답에서 테이블 구조 변경과 행 데이터 추가를 구분한다.
- 새 예시 표를 사용하면 '설명용 예시'로 표시한다.
- CREATE/ALTER/DROP의 구조 관련 역할, INSERT의 행 추가를 혼동하지 않는다.
- Oracle 트랜잭션 동작을 설명한다면 Oracle 기준과 문서 근거를 명시한다.
- CREATE 등 단어를 외우라는 장문만 보여주지 않고 표의 변화와 설명을 연결한다.
- 문구가 바뀐 새 질문에도 작동한다. 고정 DDL 영상/대본 한 개를 재생하지 않는다.

### T02. COUNT와 NULL: 실제 문제 결과
다음 SQLite 문제의 원본 표를 그대로 사용한다.
exam_result(name, score): (박강열,80), (유성재,NULL), (김현수,100)
질문: COUNT(*)와 COUNT(score)는 각각 얼마이고, 왜 다른가?
- 기준 결과는 3과 2다.
- COUNT(*)에서는 세 행을, COUNT(score)에서는 값이 있는 두 칸을 강조한다.
- 실제 모델 원시 출력과 앱 검증 후 결과를 모두 보존한다.
- 없는 score_value/grade 열을 만드는 오류가 있으면 원시 오류를 기록한다.
- 학생에게 보여주는 숫자와 음성 대사는 기준 결과와 일치해야 한다.
- 올바른 SQL을 시스템이 수정/도구로 얻었다면 그 사실을 모델 단독 성능과 구분한다.

### T03. 비어 있지 않은 칠판에서 질문 두 번과 복귀
T02의 원본 표와 첫 강조 표시가 보이는 중에
'점수가 없는데 왜 사람 수에는 들어가?'를 입력한다.
- 오디오/입/펜 동작을 중지하고 원본 표를 보존한다.
- 해당 NULL 셀과 행을 가리켜 현재 표를 이용해 설명한다.
그다음 '그럼 셋 다 점수가 없으면?'이라고 묻는다.
- 원래 문제를 몰래 바꾸지 않고 새 가정임을 명시한다.
- 같은 세 행을 유지한 가정이라면 COUNT(*)=3, COUNT(score)=0이다.
- 이전 수업 복귀 시 원래 점수 80/NULL/100과 판서 상태가 복원된다.
- 기존 표 객체 ID, 셀 값, 강조 위치, 현재 단계, 오디오 상태를 비교한다.
실제 모델·TTS·UI로 이 경로를 통과해야 한다. 빈 칠판 복귀로 대체할 수 없다.

### T04. GROUP BY / WHERE / HAVING
동봉 group_count/having 개발 예제를 활용한다.
- 필터 전 원본→WHERE 후 남은 행→그룹→집계→HAVING 후 결과가 연결돼야 한다.
- 중간 표는 검증된 입력/조건에서 계산한다. LLM이 임의 숫자를 생성하지 않는다.
- 이를 학습용 논리 설명이라고 표시하고 DB 물리 실행 추적이라고 부르지 않는다.
- 최종 SELECT 출력 형태와 중간 설명 표를 혼동하지 않는다.

### T05. 사진 원문 수정
코덱스가 직접 새로 작성한 작은 문제표 이미지를 생성해 테스트할 수 있다.
합성 이미지라는 출처를 기록하고 실제 학생 사진 전반의 성능으로 주장하지 않는다.
- 일반 텍스트 사진, NULL/숫자/표 사진, 일부 잘린 사진을 최대 3종으로 사용한다.
- 실제 인식 출력, 사용자가 수정할 항목, 최종 확정 원문을 따로 저장한다.
- 숫자 하나를 수정하면 이전 풀이/음성/판서가 무효화되고 새 값으로 계산한다.
- 잘린 사진에서 누락된 표/조건을 임의 복원하지 않는다.
사진 OCR이 실패하면 알려진 정답 텍스트를 몰래 주입해 성공 처리하지 않는다.

### T06. 문법은 맞지만 질문은 틀리게 푼 경우
'점수가 있는 사람 수' 질문에 COUNT(*)를 내는 후보를 주입한 단위 테스트를 추가한다.
- SQL 실행 성공을 의미적 정답으로 처리하지 않는다.
- 원시 스키마/문제에서 검증할 수 있는 범위와 판정 이유를 남긴다.
이것은 실패 방어 코드의 fixture 검사이고 실제 모델이 같은 오류를 냈다는 증거는 아니다.
실제 모델 실행과 분리해서 보고한다.

### T07. 조건 부족 / DBMS 차이
- '이 SQL 결과 몇이야?'만 있고 필요한 표가 없으면 구체적으로 어떤 자료가 필요한지 알린다.
- 일반 개념 질문까지 무조건 거절하지 않는다. 규칙 설명과 정확한 수치 답변을 나눈다.
- Oracle 전용 문법을 SQLite에서 실행하지 못한 것을 SQL 자체가 틀렸다고 단정하지 않는다.
- 검증 밖 문제에 확정된 답인 것처럼 새 숫자/조건을 만들어 강의하지 않는다.

### T08. busy / 취소 / 늦은 이벤트
- 학습이나 GPU 작업 점유 중 409를 받아도 입력창의 질문이 사라지지 않는다.
- 별도의 GPU 학습을 새로 실행해 시험할 필요는 없다. 기존 점유 fixture와 실제 추론 점유를 구분해 활용한다.
- 생성 취소 후 새 질문을 보내면 이전 오디오와 판서가 뒤늦게 재생되지 않는다.
- 이전 강의의 완료 이벤트가 새 강의를 completed로 만들지 않는다.

## B. 이번에 기록할 지표
- 원래 12문항의 항목별 결과와 SQL 11문항 분모 유지 여부
- 개발 회귀 예제 결과: 모델 단독 / 검증 도구 포함 앱 별도
- 올바른 최종 답, 중간 설명 오류, 잘림, 없는 열, 누락 조건 창작 건수
- 답변 가능 질문 중 실제로 답한 수 / 거절·실패 수 (모두 거절한 개선 방지)
- 사진 인식 원문 오류와 학생 수정 후 풀이 정확성 구분
- 요청부터 첫 검증된 설명/음성/판서까지의 실측 시간
- 중간 질문 재생 정지 시간과 재설명 시작 시간
- 모델 전환 시간, 실제 VRAM 상태, 캐시 적중, cold/warm 구분
- 최종 브라우저 확인 시 코드 revision/작업트리 해시와 실행 시각

## C. 통과와 실패 해석
- 테스트 개수가 증가했다고 교육 정확성이 증가했다고 말하지 않는다.
- T01~T03과 T07의 심각한 내용 오류가 남아 있으면 교육 실사용 준비 완료로 표시하지 않는다.
- 도구가 오답 전파를 막는 것과 모델이 스스로 잘 푸는 것을 각각 보고한다.
- 중간 질문의 자연스러움, 발음·청취성, 실제 이해 도움은 사람의 검토가 필요하다.
- 사용자에게 3~5개 짧은 확인 장면과 '정확함/이해됨/말·판서 일치' 체크표를 제공한다.
  실제 사용자가 확인하지 않은 체크박스를 미리 체크하지 않는다.
- 목표를 못 맞춰도 실패를 보존하고 실행 가능한 수정사항과 남은 병목을 보고한다.

## D. 최종 보고서 형식
1. 이전 상태에서 무엇을 실제로 수정했는지: 파일 경로·주요 변경.
2. SQL 오답의 주된 원인: 문항별 증거. 추측은 추측으로 구분.
3. 기존 3/11과 새 결과: 분모·설정·실험 모드·잘림·안전 중단 함께 표시.
4. 실제 질문→음성→판서→내용 있는 칠판 중간 질문→복귀 증거.
5. 지연 측정: 실제 횟수와 값. '실시간'이라는 말만 쓰지 않는다.
6. 저장 경로·전체 사용량·남은 예산.
7. 모델/어댑터 적용 상태: 학습 보류 및 기본 모델 유지 여부.
8. 자동 검증 완료 / 실제 모델 검증 / 인간 검토 대기 / 실패·차단 구분.
9. 지금 실행할 정확한 명령과 다음에 필요한 한 가지 핵심 의사결정.

상태 갱신은 기존 스키마를 깨지 않도록 확장한다.
기존 LOCAL_MVP_VERIFIED 기록은 해당 범위를 유지하고,
후속 품질 개선 결과를 별도 필드/보고서에 기록한다.
