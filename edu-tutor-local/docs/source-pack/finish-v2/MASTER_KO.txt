- 원본 display_text와 발음용 spoken_text를 구분한다. NULL/SQL/숫자 발음 변환을 기록한다.
- 오디오 파형 또는 엔진이 제공한 실제 이벤트로 입/판서를 연결한다.
  음소 정렬이 없으면 입 움직임을 정밀 lip-sync라고 표시하지 않는다.
- browser speechSynthesis는 로컬 여부·이벤트·외부 전송 여부를 검증하지 않으면 기본 경로로 쓰지 않는다.
- 캐시 재생·배속·소리 생략·고정 녹음을 신규 합성의 속도 성과로 사용하지 않는다.

후보별 동일한 짧은 새 한국어 문장으로 실제 오디오와 지연을 비교한다.
Windows 음성 또는 다른 엔진을 채택하면 'Qwen 개선'이 아니라 엔진 변경으로 표시한다.
검증한 대안이 동작하면 기본 로컬 음성에 적용하고 되돌리기 가능하게 한다.
특정 목소리의 고급 품질보다 정상적인 한국어 수업 경험을 우선한다.
사용자 캐릭터·향후 목소리 교체 구조는 유지한다.

5. 교육 내용 추가 학습 — 이번 범위에서 실제 수행

과거 demo 50step·어댑터 비교는 역사 기록이다. 그것을 새 교육 학습으로 보고하지 않는다.
실제 모델 가중치가 바뀌는 학습과 RAG/계산기/템플릿 변경을 구분한다.

교육 범위를 평가 전에 고정한다.
- DDL/DML: 표 구조와 행의 값 변경 구분
- 행/열/기본키/외래키/기본 제약조건
- SELECT/WHERE/ORDER BY/DISTINCT
- NULL/0/빈 문자열/IS NULL/조건 판단
- COUNT/SUM/AVG/MIN/MAX, 빈 입력과 NULL 처리
- GROUP BY/HAVING과 중간 계산
- 기본 INNER/LEFT JOIN
- 선택 행의 이유, 학생의 오해, 부족한 조건, 새로운 가정에 대한 보충 설명

실행 검증은 SQLite임을 명시한다. SQLD/Oracle 전체 검증으로 확대하지 않는다.
Oracle의 빈 문자열·함수·DDL/트랜잭션 차이는 공식 근거와 DBMS를 분리해 설명한다.
DDL/DML 실행은 매번 버리는 격리 DB만 사용하며 학생 DB와 앱 DB에는 실행하지 않는다.

데이터:
- 이미 가진 검토 자료와 권한 확인 자료부터 재사용한다.
- 부족한 자료는 독립 실행 검증 가능한 새 예제 생성기·계산 규칙으로 작성한다.
- 대량 ChatGPT/Codex 답변 수집·무단 교재/기출 복원·임의 웹 스크래핑을 하지 않는다.
- 각 자료에 출처, 이용권한, 검증 방식, 사람 검토 여부를 분리해 기록한다.
  이용 조건이 불명확하면 학습 제외한다. 다른 API의 학습 가능 여부도 추정하지 않는다.
- 목표는 검증된 학습 약240개, validation40개, 고정 final test80개.
  수량 자체가 학습 품질을 보장하지 않으며 검증되지 않은 문장으로 숫자를 채우지 않는다.
- 실제 값·문제 조건·SQL 결과·중간 표와 설명의 주장까지 대조한다.
  SQL이 실행된다는 사실만으로 질문에 맞는 정답이라고 승인하지 않는다.
- problem_family_id로 나눠 같은 문제의 이름/숫자 변형이 train/test로 흩어지지 않게 한다.
- 기존18/54문항·실패E는 개발 회귀 세트다. 신규 final의 정답과 해설을
  학습·RAG·프롬프트·제품 캐시에 넣지 않는다.
- final을 보고 다시 수정하면 그 세트는 개발 세트가 된다. 새로운 final이 없으면
  독립 평가 완료라고 쓰지 않는다. 사람 검토 전 자료에 human-reviewed를 붙이지 않는다.

모델 기준선과 선택:
- 기존 Qwen3-1.7B 및 tokenizer/template, 입력 길이, 잘림, 응답 마스킹을 확인한다.
- 기준선은 새 입력으로 실행한다. 저장 답변 재채점을 새 성능이라고 쓰지 않는다.
- validation에서 기초 설명이 계속 불충분하면 신규 모델 후보1개를 예산 안에서 비교 가능하다.
- 크기/최신 여부만으로 선택하지 않는다. 정확도·한국어 설명·VRAM·지연을 함께 기록한다.
- 교체는 실측 후 결정한다. 8GB에서 실행·학습된다고 추정만 하지 않는다.
- 모델 실행·학습 경로는 TTS 실험 bootstrap에 의존하지 않게 한다.

추가 학습:
- 안정된 기존 PyTorch/Transformers/PEFT 경로로 LoRA/QLoRA 실험을 실제 실행한다.
- microbatch1, 적절한 accumulation/길이/checkpointing 등 검증된 설정에서 시작한다.
- assistant 응답 label, EOS/PAD, Qwen 생각 모드/template를 실제 토큰으로 확인한다.
- smoke만 하고 본 실험 완료라고 하지 않는다. 검증된 데이터로 실제 학습을 진행한다.
- 데이터 해시, 모델 revision, 학습 대상 수, step, adapter 변경, loss, 메모리를 기록한다.
- 저장 adapter를 새 프로세스에서 같은 base와 다시 읽고 응답을 생성한다.
- 학습 재개 상태를 저장하지 않았으면 adapter 저장을 optimizer 재개 지원이라고 쓰지 않는다.

평가와 적용:
같은 조건에서 base/adapter OFF·ON과 app(검색·계산 연결) 결과를 구분한다.
validation으로 선택하고 final은 판정에 사용한다. 모델 교체와 추가 학습 효과도 분리한다.
loss 감소나 50/600step 자체를 교육 향상으로 표시하지 않는다.
두 번째 학습은 validation에서 확인한 원인과 수정 가설이 있을 때만 실행한다.
명백히 나빠진 adapter는 기본 적용하지 않고 TRAINED_NOT_PROMOTED로 남긴다.
실제 학습이 없으면 해당 상태를 쓰지 않는다. 실패하면 정확히 NOT_RUN 또는 FAILED다.
권한·데이터·독립 실행 문제로 학습이 막히면 해당 트랙만 차단 표시하고 나머지를 계속한다.

6. 새 질문에서 강사처럼 설명하는 경로

가능하면 텍스트 모델을 한 수업 동안 준비 상태로 유지해 반복 cold 비용을 줄인다.
작동하는 기존 경로를 우선하고 실패한 음성 launcher를 그대로 공용화하지 않는다.
세부 신경망 관측은 기본 OFF다. GPU 모델 여러 개 동시 상주는 실제 여유와 동작을 확인한다.
학습과 학생 추론은 병렬로 실행하지 않는다.

교사 설명은 짧고 완결된 단계로 구성한다.
질문의 목표→필요한 개념→원본→중간 변화→결과→이유→보충 질문.
완성된 긴 강의나 영상을 전부 만들어야 첫 소리가 나오게 하지 않는다.
첫 유효 설명은 질문 내용에 답하는 문장이어야 하며 '잠시 기다리세요'는 제외한다.

하나의 evidence/lesson step에서 대사·표·그림·강조·캐릭터 target을 파생한다.
지원 범위의 계산은 실행 결과와 독립 근거를 대조한다.
모델 원답, 앱의 수정 내용, 근거 자료를 구분해 저장한다.
특정 질문 문자열·테이블 이름·정답에 맞춘 하드코딩은 하지 않는다.
공통 연산 규칙이나 설명 형식은 사용 가능하지만 모델 단독 능력으로 보고하지 않는다.

개념 질문은 SQL이 없다는 이유로 모두 거절하지 않는다.
자료가 없는 문제는 없는 표/조건을 지어내지 않고 필요한 부분만 물어본다.
RAG는 근거 개념을 검색하는 것이며 정답표를 몰래 넣는 평가 우회가 아니다.
출처가 존재하거나 SQL 실행에 성공했다는 이유만으로 해설 전체를 정답이라고 판정하지 않는다.

칠판/캐릭터:
- 원본 표, 중간 표, 최종 결과가 같은 값을 사용한다.
- 글·코드·수식은 명확하게, 보조 그림은 선·화살표·상자·간단한 관계도로 표현한다.
- 쓰기 손/펜 끝과 실제 그림 경로는 같은 좌표계를 사용한다.
- 단순 텍스트 출현 효과를 정확한 사람 획순이라고 주장하지 않는다.
- 현재 설명 중 다음 한 단계만 준비하며 취소된 plan·WAV가 섞이지 않게 한다.
- 중간 질문이면 음성을 즉시 멈추고 판서 상태·선택 셀·단계·진행 위치를 보존한다.
- 실제 현재 행을 활용해 보충하고 원래 수업으로 복귀한다. 같은 뜻의 바꿔 말한 질문도 시험한다.
- 새로운 가정은 원본 데이터와 구분한다. 늦은 응답이 새 수업을 덮어쓰지 않게 한다.
- 긴 표·390px 화면·글자 확대에서 선택 대상과 설명이 가려지지 않게 한다.

7. 사진 입력과 후속 질문

기존 인식·편집·확정 경로를 재사용한다.
문제의 질문/SQL/표/선택지와 잘린 조건을 함께 보존한다.
원본 이미지와 추출 내용을 보여주고 중요한 불명확 부분만 확인하게 한다.
텍스트 수정 후 이전 revision의 답변·음성·판서를 폐기한다.

실제 사진 인식 모델로 권한 있는 신규 개발 이미지를 읽어 검증한다.
정상 표/SQL, 회전·흐림, 조건이 잘린 경우를 구분한다.
사진의 기대 원문을 모델 입력으로 넣지 않는다.
수동 원문 입력과 자동 인식 성공을 구분한다.
필요한 재인식은 요청당 최대1회이며 전체30회 한도에 포함한다.
사진이 막히더라도 텍스트 수업 개발을 계속하되 사진 완료라고 하지 않는다.

8. 최종 같은 버전의 실측과 합격 기준

현재 코드·설정·모델·adapter·TTS 엔진을 고정하고 검사한다.
마지막 수정 뒤 영향 검사를 다시 한다. 다른 시점의 테스트를 합산해 최종 전체 통과로 쓰지 않는다.

정확성:
- 지원 범위 final80개의 원시모델/학습전후/도구 연결 결과를 가능한 조건별로 구분한다.
- 범위 내 실질 응답90% 이상, 자동 판정 가능한 정답/중간 계산90% 이상을 후보 기준으로 둔다.
- 이 기준은 제품 평가 목표이며 달성 보장이나 업계 표준이 아니다.
- 거절/미지원/잘림을 정답으로 넣지 않는다. 답한 비율과 답한 것의 정확도를 함께 보고한다.
- 핵심 개념 오답이 음성으로 전달된 사례가 남으면 별도로 표시하고 READY로 승격하지 않는다.
- 유한 검사에서 중대오류0인 것과 앞으로 모든 질문에서 오류가 없다는 주장을 구분한다.
- 설명의 친절함/이해도는 자동 검사와 실제 사람 판단을 분리한다.

지연:
- 준비된 모델에서 새 질문→첫 유효 설명 목표10초, 새 보충 목표10초.
- 불필요한 단계 공백 목표2초, 로컬 재생 정지 목표0.5초.
- cold 로딩은 따로 보고한다. 임의로 모델을 준비해 놓고 cold라고 하지 않는다.
- 최소10개의 새 질문/보충 시나리오에서 원시 시간·성공률·중앙값·최댓값을 기록한다.
- 녹음 캐시 재생과 신규 합성을 구분한다. 모델 warm과 OS 파일 warm도 구분한다.
- 첫토큰·계획·첫오디오 준비·첫재생은 별도 지표다. 서로 다른 시계/중첩 구간을 합산하지 않는다.
- 사진 업로드→원문후보, 사람 확인시간, 원문확정→첫설명을 분리한다.
- 실패/timeout을 지연 평균에서 몰래 제외하지 않는다.

실제 전체 수업:
같은 최종 버전에서 새로운8개 수업 여정을 시험한다.
개념2, 표 계산/작성2, 그룹/JOIN·간단한 그림1, 정상 사진2, 누락 조건 사진1.
8개 중 실제 중간 질문 최소2회, 내용 있는 표의 선택 행 질문,
캐릭터 쓰기·가리키기, 간단한 그림, 정지·보충·복귀를 포함한다.
전체 수업은 실제 모델과 실제 음성을 사용하고 고정 녹음·fixture로 대체하지 않는다.
취소·재시작·캐시 누락·최종 빌드 반복 사용도 확인한다.

사람 검토:
기존 갤러리에 대표 수업3~5개를 열어 볼 수 있게 정리한다.
실제 검토자 입력 없이 H_PENDING을 지우거나 사람의 들은 발화를 자동 작성하지 않는다.
사람 검토가 없으면 기술적으로 검증된 검토용 버전까지 배포하고,
교육 실사용 승인과는 구분한다. 사람 검토 대기를 전체 코드 작업의 중단 이유로 쓰지 않는다.

9. 실제 적용·배포·최종 인계

수정 파일을 저장한 것과 실행 중인 서버에 반영한 것은 다르다.
앱의 활성 작업과 소유 프로세스를 확인하고 필요한 정상 종료·재시작을 수행한다.
시작 스크립트와 새 PID·빌드·설정·실제 엔진·어댑터로 반영 여부를 확인한다.
무관한 프로세스나 사용자의 다른 개발 서비스를 종료하지 않는다.

실제로 검증된 모델·음성 구성만 기본값으로 선택하고 rollback을 제공한다.
사용 안내는 기존 README와 실행 스크립트를 갱신한다.
소스 릴리스는 코드·설정 예시·필요한 설치 정보만 포함하며 키/토큰/학생DB/업로드/
가상환경/대형 가중치를 포함하지 않는다. 본문에 auth-token을 출력하지 않는다.

기존 상태 문서의 최신 부분만 일관되게 갱신한다.
과거 실패 파일은 보존하되 매 인계마다 과거 전체 브리핑을 통째로 복사하지 않는다.
매 단계마다 전체 모델·DB·수백 파일 해시를 반복 생성하지 말고,
필요한 snapshot과 최종 실행 manifest를 남겨 보존과 실제 기능 확인에 집중한다.

최종 보고 첫 부분은 아래 순서다.
1) 오늘 실제로 무엇을 바꿨고 사용자가 이전과 달리 무엇을 할 수 있게 됐는가?
2) 교육내용 학습을 실제 했는가? 데이터/모델/step/adapter/전후/적용 여부는?
3) 어떤 새 질문에 어떤 설명·판서·음성이 나왔고 실제 대기시간은?
4) 현재 기본 엔진과 버전, 같은 빌드의 검증 범위는?
5) 남은 문제와 실패한 대안, 필요한 사람 검토·권한·자원은?
6) 저장·다운로드·모델 작업 사용량과 잔여는?
7) ChatGPT 전달용 — 그대로 복사

인계문에는 현재 실제 시각·시간대, 프로젝트 경로, 코드 버전/확인 불가,
실행 증거(run ID), 이번 변경, 현재 사용자 경험, 미완료, 다음 정확한 작업을 넣는다.
낡은 2026-10-27 보고서를 날짜만 바꿔 새 결과처럼 내지 않는다.

상태 판정은 실제 근거에 따른다.
- NOT_READY: 핵심 기능/속도/정확성이 검증되지 않았거나 실패가 남음.
- ENGINEERING_VERIFIED_REVIEW_PENDING: 고정 범위의 기술 기준 통과, 사람 검토 대기.
- 교육 사용 승인: 해당 범위의 실제 사람 검토 근거까지 확보했을 때만.
모델 학습 실패 또는 미적용도 별도 표시한다. 프로그램 기능과 모델 능력을 섞지 않는다.

이번 목표는 '다음에는 native 예외를 더 조사해야 한다'는 같은 인계를 반복하는 것이 아니다.
현재 지시 수신과 실제 예산 적용을 확인하고, 새 한국어 음성 경로 및 교육 모델 학습을
서로 독립적으로 진행해 새 질문의 수업까지 연결하고 검증하는 것이다.
예산/권한/세션이 실제로 끝날 때까지 가능한 승인 작업을 이어가되,
완료하지 못한 것을 완료했다고 쓰지 말고 정확한 현재 결과를 남겨라.
