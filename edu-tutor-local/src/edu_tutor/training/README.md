# Training evidence boundaries

`tiny.tiny_lora_smoke(output_dir)` runs real FP32 CPU LoRA on a tiny, randomly initialized Qwen3. It saves that exact tiny base once as safetensors, checks finite loss/gradients, real adapter updates, frozen base equality and eval logits after reloading the saved adapter onto the same base. It is not an educational model.

`runner.run_gpu_training(config_path, model_path, output_dir, mode='smoke', dataset_paths=None, local_dir=None, cancel_event=None, job_id=None)` runs bounded actual local QLoRA. Only pinned local Qwen3-1.7B safetensors are accepted. It never fetches models. Separate training and reload processes use the application GPU lease. Smoke is 5 optimizer steps with gradient accumulation 8, not 5 microbatches. Demo is at most 50 steps and requires a completed matching smoke/reload. One demo attempt is permitted per dataset hash. Hard process caps are 600/900 seconds including reload.

Training uses NF4 double quantization, verified BF16 support (otherwise FP16), single CUDA device, PEFT preparation, rank 8 LoRA on q_proj/v_proj, AdamW, batch 1, sequence cap 512 and response-only labels. Overlength samples are excluded with IDs and reasons; their answers are never silently truncated. Tokenizer template stability is checked with actual token IDs. EOS is retained even if the padding ID equals EOS. Full target audits are local files.

Adapters are never promoted automatically. Adapter files are weights only; true optimizer/scheduler/RNG/data-position resume is not implemented. A cancelled worker gets up to 20 seconds to save at the next optimizer-step boundary, after which its process is terminated and the run stays interrupted. T2 execution, small-dataset comparative evaluation and human education quality review are distinct evidence.

Each optimizer step checks the small trainable LoRA weights for finite values, in addition to the pre-step gradient and logged-loss checks. Live metrics use directly counted microbatches: `samples_per_second` is cumulative processed samples divided by time since training started, including repeated epochs. `current_vram_bytes` and `peak_vram_bytes` are CUDA allocator bytes, not total device memory usage; peak begins at the worker reset before model loading. Old logs are never backfilled with unmeasured samples. The actual GPU evidence used BF16; the FP16 fallback has no separate hardware-validation evidence.

Official implementation references checked during development: [Qwen model card](https://huggingface.co/Qwen/Qwen3-1.7B), [PEFT quantization](https://huggingface.co/docs/peft/en/developer_guides/quantization), [Transformers Trainer](https://huggingface.co/docs/transformers/main_classes/trainer). Installed-package imports and run manifests, rather than documentation alone, determine the executed compatibility evidence.
